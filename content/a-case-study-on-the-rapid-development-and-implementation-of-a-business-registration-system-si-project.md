# [프로젝트 회고] 기업카드 앱 '사업자 제신고' 신속개발 SI 구축기

![금융 IT 시스템 아키텍처 및 백엔드 개발 환경](https://images.unsplash.com/photo-1551288049-bebda4e38f71?w=800&auto=format&fit=crop&q=60)

## 1. 프로젝트 개요

기존에 영업점 방문이나 오프라인 서류 제출 위주로 처리되던 **기업카드 '사업자 제신고(사업자 정보 변경, 카드 관리, 각종 신청·신고 등)' 업무를 기업카드 전용 모바일 앱 내에서 비대면으로 완결**할 수 있도록 구축한 신속개발(Agile/Fast-track) SI 프로젝트에 백엔드 개발자로 참여했습니다.

* **주요 목표:** 기업 고객(법인/개인사업자)의 모바일 채널 접근성 강화 및 비대면 셀프 제신고 프로세스 구현
* **개발 환경:** Java 8, Spring Framework, eGovFrame, MyBatis, Tibero, Eclipse, Jenkins, SVN
* **연계 아키텍처:** 채널계(카드플랫폼) ↔ MCA ↔ 계정계(CRD) ↔ 대외계(FEP/BC카드) 및 EAI/UMS 비동기 알림 연계

> **💡 핵심 아키텍처 포인트**
> 짧은 구축 기간 내에 기존 계정계 원장과 대외 기관(BC카드) 인터페이스를 안전하게 연결하기 위해, 채널계의 비동기 알림 분리와 전문 매핑 표준화에 집중했습니다.

---

## 2. 주요 담당 업무 및 구현 내용

### ① 사업자 제신고 비대면 백엔드 API 및 비즈니스 로직 개발

* **자격 검증 로직 구현:** 기업회원 구분(`법인공용`, `법인지정자`, `개인사업자` 등)과 카드 상태 라이프사이클(정상, 정지, 만료, 재발급 등)에 따른 세밀한 제신고 자격 검증 분기 처리
* **데이터 무결성 및 정밀 연산:** 레거시 화면(JSP) 및 모바일 채널 요청 파라미터의 Null 안전성을 확보하고, 금액 및 수치 연산 오차 방지를 위해 `BigDecimal` 기반 정밀 데이터 처리 적용
* **표준 전문 송수신:** 공통 헤더(`CommHeader`) 초기화 및 표준 인터페이스 버스(SCIB) 규격에 맞춘 전문 송수신 모듈 개발

### ② 계정계·대외계(MCA / FEP) 전문 연계 및 대량 데이터 페이징 처리

* **전문 자동 매핑 구조:** 계정계(CRD) 및 BC카드 원장 시스템과의 전문 통신을 위해 **MMS(Message Meta System)** 기반의 입출력 VO 자동 생성 및 매핑 구조 설계
* **연속 거래 페이징 구현:** 1회 조회 건수 제한이 있는 결제·수납 내역 및 카드 목록 조회 시, 공통 헤더의 **연속거래구분코드**(`CtntTrnDcd`)와 `do-while` 루프를 활용한 연속 조회(Pagination) 로직 구현
* **거래 데이터 정합성 매핑:** 일반 가맹점 승인 내역과 선결제·수납 내역이 혼재된 결제 데이터에서 수납처 코드와 거래 유형을 정확히 분류하여 채널 화면에 매핑

### ③ EAI 및 UMS 기반 비동기 알림 파이프라인 분석·연계

* **실시간 고객 알림 파이프라인:** 카드 승인 및 제신고 처리 완료 후 고객에게 실시간 알림(앱 푸시 및 알림톡/SMS 대체 발송)이 전달되는 비동기 아키텍처 연계
* **트랜잭션 정합성 보장:** DB 트랜잭션 롤백 시 오발송을 방지하기 위해 메인 비즈니스 로직 커밋 직후 외부 전문을 발송하는 **`sendAfterCommit` (Transactional Outbox 패턴)** 흐름 적용 및 UMS(통합 메시징 시스템) 연계

## 3. 트러블슈팅 및 기술적 인사이트

### 🔍 폐쇄망 개발 환경에서의 MMS 플러그인 통신 타임아웃 해결

* **문제 상황:** 이클립스 내 전문 자동 생성 툴(`Import MMS`) 실행 시 `NullPointerException` 발생 후, 메타 서버 조회 단계에서 15초 타임아웃(`cannot connect to pluginserver`)으로 전문 로딩이 실패하는 현상 발생
* **원인 분석:**
  1. 프로젝트 설정 파일(`Project.mf`) 내 템플릿 경로 오류 수정 후 UI 진입은 성공했으나, 실제 조회 시점에서 네트워크 단절 확인
  2. OS 레벨(`netstat` 및 `Test-NetConnection`)로 실제 호출 대상 메타 서버의 IP/Port와 방화벽 오픈(`TcpTestSucceeded: True`) 여부를 교차 검증하여, 단순 방화벽 차단이 아닌 **로컬 PC IP 접근 권한(ACL) 및 사용자 매핑 누락**임을 규명
* **해결 결과:** TA 및 인프라 담당자에게 정확한 타겟 IP:Port 및 통신 테스트 증적을 전달해 ACL 권한을 등록함으로써 개발 생산성 정상화

> **💡 폐쇄망 네트워크 디버깅 교훈**
> 방화벽 오픈(`TcpTestSucceeded: True`)이 곧 애플리케이션 레벨의 통신 성공을 보장하지 않습니다. 미들웨어나 메타 서버단의 IP ACL 정책까지 단계별로 교차 검증하는 습관이 불필요한 대기 시간을 크게 줄여줍니다.

### 🔍 레거시 환경에서의 방어적 코딩과 트랜잭션 분리

* **잠재적 결함 개선:** 레거시 코드베이스 분석 과정에서 루프 내부의 잘못된 `BigDecimal` 초기화 로직이나 단일 객체만 담는 이중 중괄호(`{{ }}`) 컬렉션 초기화(익명 클래스 생성으로 인한 메모리 누수 위험) 등 잠재적 결함 요소를 점검하고 표준 Collection 및 누적 패턴으로 리팩토링
* **스레드 및 디퍼드 연동 안정화:** 온라인 메인 트랜잭션의 응답 속도를 저하시키지 않기 위해 스레드 풀(`ExecutorService`)의 Graceful Shutdown(`@PreDestroy`) 관리와 EAI/디퍼드(Deferred) 연동 구조를 명확히 구분하여 시스템 안정성 확보

## 4. 프로젝트를 마치며 (회고)

짧은 기간 안에 핵심 기능을 빠르게 오픈해야 하는 **신속개발 SI** 특성상, 새로운 기능 구현만큼이나 **기존 금융 코어 시스템(MCA/EAI/FEP)의 데이터 흐름과 도메인 제약사항을 정확히 이해하는 것**이 중요했습니다.

이번 프로젝트를 통해 채널계 백엔드 개발자로서 단순 API 작성을 넘어, 계정계 전문 설계부터 비동기 메시징, 폐쇄망 인프라 트러블슈팅까지 엔드투엔드(End-to-End) 금융 IT 아키텍처를 깊이 있게 다룰 수 있었습니다.
